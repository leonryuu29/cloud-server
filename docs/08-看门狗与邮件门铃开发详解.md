# 看门狗与邮件门铃 · 开发详解

> 和 `05-MCP开发详解.md` 是姊妹篇：05 讲「给 AI 用的工具」怎么写，这篇讲「不用 AI 的后台程序」怎么写。
> 代码：`watchdog.py`、`mail_check.py`（本地 `T:\云服务器\dafeiyu-mcp\`，服务器 `/root/dafeiyu-mcp/`）

## 1. 为什么要有它们，为什么不做成 MCP 工具
MCP 工具是**大肥鱼（AI）主动调用**的。但有两类事不适合交给 AI：

| 事情 | 交给 AI 的问题 | 所以用普通脚本 |
|---|---|---|
| 盯着大肥鱼、坏了就修 | 大肥鱼卡住/掉线时，正是它最没法自己调工具的时候；修复动作（重启、重跑）不该让 AI 拍脑袋 | **看门狗** `watchdog.py` |
| 经常检查邮箱 | 每 10 分钟问一次 AI，一天上百次，大多数时候“没新邮件”，白花钱 | **邮件门铃** `mail_check.py`：代码先看，有事才叫醒 AI |

两者都是**系统 cron 定时叫醒 → 读数据 → 按写死的规则做事 → 写日志 → 退出**，不常驻、不花 token。

```
           系统 cron（/etc/cron.d/）
          ┌───────────┴───────────┐
   每 10 分钟                   每 10 分钟（德国 7–23 点干活）
   watchdog.py                  mail_check.py
     │ 读 AstrBot 数据库/日志      │ IMAP 只看 WEB.DE（不推进位置）
     │ 修：补发/重启/补货/清理      │ 有非广告新邮件？
     ▼                            ▼
   AstrBot 后台接口  POST /api/v1/cron/jobs/{id}/run   ← 两者共用：叫 AstrBot「立即执行某个任务」
     │                            │
   重跑没发出的推送             跑「重要邮件」任务 → 大肥鱼调 MCP 工具 new_emails → 判断 → QQ
```

## 2. 怎么让脚本能“叫” AstrBot：后台接口 + 令牌
AstrBot 的网页后台背后是一套 HTTP 接口，网页能做的事接口都能做。我们用到的：

| 接口 | 作用 |
|---|---|
| `GET /api/v1/cron/jobs` | 列出所有定时任务 |
| `POST /api/v1/cron/jobs` | 新建任务 |
| `PATCH /api/v1/cron/jobs/{id}` | 修改任务（比如改说明） |
| `POST /api/v1/cron/jobs/{id}/run` | **立即执行**一个任务（会忽略“是否启用”） |

接口要登录。我们先试了 API Key，发现 AstrBot 的 API Key 不支持这些接口要求的 `system` 权限（报错 `Invalid scopes: system`）。翻源码发现网页登录用的是 **JWT 令牌**，用配置里的 `jwt_secret` 签名。服务器本机能读到这个配置，所以脚本自己签一个就行：
```python
import jwt, json, datetime as dt
dash = json.load(open("/root/astrbot/data/cmd_config.json", encoding="utf-8-sig"))["dashboard"]
token = jwt.encode({"username": dash["username"],
                    "exp": dt.datetime.now(dt.timezone.utc) + dt.timedelta(minutes=5)},   # 5 分钟就过期
                   dash["jwt_secret"], algorithm="HS256")
# 请求头：Authorization: Bearer <token>，地址：http://127.0.0.1:6185/...
```
安全上：只在服务器本机（127.0.0.1）用；令牌 5 分钟过期、不存盘、不打印；6185 端口不对外开放。

## 3. 看门狗 watchdog.py 逐段讲
### 3.1 判断“推送有没有发出”
AstrBot 数据库 `data_v4.db` 的 `cron_jobs` 表记着每个任务的 `last_run_at`（上次运行时间，UTC）。大肥鱼真发出消息时，日志里会有一行 `send_message_to_user ... Message sent`。
```python
for job_id, name, last in 启用的任务:
    t = last_run_at
    if not (6 分钟 <= 现在 - t <= 40 分钟): continue     # 只管刚跑完的，不翻旧账
    if 日志里 [t, t+5分钟] 有 "Message sent": continue   # 送达了
    → 没发出 → 调 /run 补发
```
为什么等 6 分钟：给大肥鱼 5 分钟时间干完活（查天气、画图都要时间），再判断。

### 3.2 刹车：最多补发一次
`watchdog_state.json` 里记每个任务的补发记录：
```json
"retried": {"<job_id>": {"orig": "原运行时间", "at": "补发那次的运行时间", "gave_up": true}}
```
- 第一次发现没发出 → 补发，记 `orig`
- 下一轮：任务的 `last_run_at` 变成补发那次 → 记到 `at`
- 补发那次也没发出 → 标 `gave_up`，**不再补**，留给服务器日报报 ×
- 记录只留 3 天

没有这个刹车，一个本身就有问题的任务会被每 10 分钟重跑一次，一直烧钱。（规则 R9）

### 3.3 其他自愈
| 检查 | 动作 | 刹车 |
|---|---|---|
| `systemctl is-active astrbot` 不是 active | `systemctl restart astrbot` | — |
| 最近一次启动后日志里没有 `Connected to MCP server dafeiyu`（且已启动 2 分钟以上） | 重启 AstrBot | 1 小时最多 1 次 |
| 图库里没发过的图 < 6 张 | 后台跑 `fetch_images.py` | 已经在补就不重复开 |
| 磁盘 > 90% | 删 3 天前的 `dafeiyu_*` 临时图 | 只删自己生成的临时图 |

### 3.4 看门狗自己怎么不出事（规则 R10）
```python
for step in (record_retry_runs, check_pushes, self_heal):
    try:
        step(state)
    except Exception as e:          # 一步出错只记下来，别的步骤照常
        errors.append(...)
state["heartbeat"] = now            # 心跳：服务器日报看它，超过 25 分钟没更新就亮红灯
trim(LOG)                           # 日志只留最后 500 行
```
cron 那一行也加了三层保护：
```
*/10 * * * * root flock -n /run/dafeiyu-watchdog.lock timeout 120 nice -n 10 python watchdog.py
```
- `flock -n`：上一次还没跑完，这次直接不跑（防叠加）
- `timeout 120`：超过 2 分钟强制结束（防卡死）
- `nice -n 10`：低优先级，不抢大肥鱼的 CPU

实测：每次 0.44 秒、33 MB，跑完就退出。

### 3.5 互相监控
- 看门狗盯大肥鱼：推送、服务、MCP、图库、磁盘
- 大肥鱼盯看门狗：MCP 工具 `server_report` 读 `watchdog_state.json` 的心跳，画成服务器日报里的「看门狗」灯，并显示「自动修复 24h N 次」「已补发」

## 4. 邮件门铃 mail_check.py 逐段讲
### 4.1 邮箱位置：只处理“上次之后”的新邮件
IMAP 里每封邮件有一个递增编号 **UID**。我们在 `state.json` 里记“处理到第几号”：
```json
"mail_pos": {"you@web.de/INBOX": {"validity": "1795349449", "uid": 2739}}
```
`validity`（UIDVALIDITY）是邮箱的“版本号”，邮箱重建时会变；变了就重新记位置，不翻旧账。

### 4.2 同一个函数，两种模式（server.py 里的 `_mail_scan`）
| 调用 | 谁用 | 会不会推进位置 |
|---|---|---|
| `_mail_scan(advance=False)` | 门铃、体检、验收 | **不会**，只看 |
| `_mail_scan(advance=True)` | MCP 工具 `new_emails`（大肥鱼真正处理时） | 会 |

这样体检、验收、门铃永远不会把真邮件“吞掉”。（规则 R12，这是测试时踩出来的坑）

### 4.3 过滤旧邮件
WEB.DE 代收 Gmail 时，会把几千封旧邮件陆续搬进来：**编号是新的，日期是旧的**。所以只认：
```
UID > 上次位置   且   邮件 Date 在 48 小时内
```
先只取邮件头的日期（很省流量），过滤完才取正文（每封只要前 300 字）。

### 4.4 门铃的判断流程
```python
found = _mail_scan(advance=False)                # 1. 看一眼
if not found: return                             #    没新邮件 → 退出（大多数时候走这里）
worth = [m for m in found if not is_noise(m)]    # 2. 代码层过滤广告发件人
if not worth:
    _mail_scan(advance=True); return             #    全是广告 → 直接标记处理过，不叫醒 AI
if 签名 == 上次叫醒时的签名: return               # 3. 同一批只叫醒一次（防反复花钱）
run_job_now("重要邮件")                           # 4. 叫醒大肥鱼
```
`NOISE_DOMAINS` 只放**肯定不重要**的发件域名（LinkedIn、Fantia、TikTok、Facebook、FROM JAPAN、Termius…）。拿不准的（Google、银行、学校、快递）一律不放，交给大肥鱼判断。

### 4.4.1 门铃心跳（2026-11-22 补）
门铃原来只在“叫醒大肥鱼”时写日志。如果 WEB.DE 密码改了、登录报错，它会每 10 分钟静悄悄地失败，谁也不知道。所以每次运行结束都写 `mail_check_heartbeat.json`（时间 + 有没有出错），`acceptance.sh` 检查“25 分钟内运行过且没出错”。夜里 0–7 点门铃直接退出，但也照样写心跳。

### 4.5 「重要邮件」任务为什么设成“不启用”
- 它不该按钟点跑，只该被门铃叫醒
- AstrBot 的「立即执行」会忽略是否启用（源码 `run_job_now → ignore_enabled=True`）
- 看门狗只检查启用的任务 → 大肥鱼判断“全是广告、不用发”时，不会被当成“推送没发出”去补发

### 4.6 大肥鱼那一侧（AI 的活）
任务说明（`重要邮件` 的 note）告诉它：先调 `new_emails` → 判断重要（考试、学校、账单、快递、合同/房租/保险、账号安全、需要回复的）→ 有重要的就用大肥鱼语气、每封一行、只说重要的 → **必须**调 `send_message_to_user` 发出；全是广告就什么都不发。

### 4.7 其他细节
- **加锁**：`_mail_scan` 用文件锁（`fcntl.flock`），防止大肥鱼同时调两次读乱位置
- **一次最多 15 封**：超过的不丢，位置只推进到处理过的最后一封，剩下下一轮处理
- **只读邮箱**：用 `BODY.PEEK`，不会把邮件标成已读
- **密码**：`config.json`（600），通过电脑上的 `set-mail.ps1` 经 SSH 直接写到服务器，不经过聊天

## 5. 两个程序共用的写法（以后写新的后台程序照抄）
1. **纯代码、跑完即退**：cron 叫醒，不常驻
2. **cron 行三件套**：`flock -n` + `timeout` + `nice`
3. **每一步 try/except**，错误写日志，不让一步拖垮全部
4. **有动作就有刹车**：次数上限 + 冷却时间
5. **有动作就有日志**，并且能在服务器日报 / 验收里看到
6. **要叫 AI 时**：通过后台接口 `/run` 叫醒一个专门的任务，而不是自己调 DeepSeek
7. **只读和写分开**：检查用只读版本，真正处理才写
