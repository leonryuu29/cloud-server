## 一、规则（加新功能/新定时任务时必须遵守）

### R1 定时任务必须明确要求「调用发送工具」
- AstrBot 的定时任务（未来任务）在**后台**运行：大肥鱼干完活，**只有调用 `send_message_to_user` 的内容才会发给主人**，写在「最终回复」里的文字会被直接丢掉
- 所以每个任务说明末尾都要有这句：
  > 【必须】最后一定要调用 send_message_to_user 工具把要说的话（和图片）发给主人——只写在最终回复里的文字不会被发出去。

### R2 「[CronJob]」是内部记录，不是推送失败
- 每次定时任务跑完，系统会往大肥鱼的聊天记录里塞「Output your last task result below」和「[CronJob] 任务名: 任务说明」，**主人看不到**
- 人格里已写明这一点，避免大肥鱼误以为推送坏了
- 排查推送以服务器日志为准：`Tool send_message_to_user Result: Message sent` = 真的发出去了

### R3 按「夜猫子日」统计
- 凌晨 0:00–5:00 的聊天算前一天（日报、聊天记录工具都按这个算）

### R4 任务说明里不给示例句子
- 给了示例，大肥鱼每天都照着说，很机械；只说「做什么」和「按你自己的口吻」

### R5 多条消息分批发
- QQ 官方机器人主动消息有额度，一次连发太多可能被吞：美图 15 张拆成 06:30 / 06:45 / 07:00 三批，图和话穿插

### R6 能用代码算的不让 AI 算
- 统计、计数、时间、去重、送达检查都由代码做；AI 只负责「理解」和「说话」（风格判断、点评、总结）→ 省 token、结果准确

### R7 改之前先备份，改完要验证
- 改 AstrBot 数据库前：`astrbot-backup` → 停服务 → 改 → 启动
- 新功能上线前：服务器上直接调用测一遍；有图的先亲眼看效果图；推送类的用一个「3 分钟后执行」的临时任务真实发一次，确认 `Message sent` 后删掉临时任务

### R8 安全
- 不给大肥鱼开 Computer Use / 执行命令；需要新能力就写一个**只做一件事**的 MCP 工具
- 密钥、授权码、登录态文件 chmod 600，不进 Git

### R9 自动修复要有刹车
- 每种修复都有次数上限和冷却：一条推送最多补发 1 次；因 MCP 掉线重启 AstrBot 1 小时最多 1 次
- 每次修复都写进 `watchdog.log`，并在服务器日报里显示（「自动修复 24h N 次」「已补发」）→ 不允许静默修复，也不允许无限重试
- 修不好就停手，交给服务器日报报 ×，由人来看

### R10 监控程序自己也要被监控，而且要轻
- 看门狗每一步单独兜底，一步出错不影响其他步骤；自身出错也写日志
- 每次运行写心跳，服务器日报检查心跳：超过 25 分钟没巡检 → 「看门狗」亮红灯（大肥鱼和看门狗互相盯）
- 用 `flock` 防重叠、`timeout 120` 防卡死、`nice` 低优先级；日志只留最后 500 行
- 跑完即退出，不常驻：实测每次 0.44 秒、约 33 MB 内存

### R11 先用代码看一眼，有事才叫醒 AI
- 需要“经常检查、偶尔有事”的功能（邮件、以后的提醒类），用系统 cron 跑普通脚本先检查；真有新东西才通过后台接口叫醒大肥鱼的任务
- 被叫醒的任务设成「不启用」：不会自己按时跑，看门狗也不会把它的“没发消息”当成故障
- 同一批东西只叫醒一次（记签名），防止 AI 没处理时每小时反复花钱

### R12 测试不能改动生产状态
- 体检、冒烟测试只能“只读”：会推进位置、标已读、改数据库的函数，在体检里一律换成只读版本（例：`_mail_scan(advance=False)`）
- 端到端测试用带「[大肥鱼测试]」标记的数据，测完记录在这里

### R13 中文路径不走 PowerShell，拷完要核对
- PowerShell 5 的命令行里写中文路径会乱码，而且 Copy-Item / scp 可能失败却不显眼 → 涉及 `T:\云服务器\...` 的读写一律用 Desktop Commander 文件工具或 node 脚本
- “synced / copied” 不算数，要用脚本列出目标目录核对（文件数、大小）

- **踩坑 4：体检会吞邮件**。healthcheck 原来直接调 `new_emails`（会推进位置）→ 改成只读的 `_mail_scan(advance=False)`（新规则 R12）

### 2026-11-22 下午：看门狗，从「报出来」升级到「自己修」
- **需求**：服务器日报只会报 ×，还得人来处理 → 希望常见问题自己修好，保持高水平运维
- **做法**：`/root/dafeiyu-mcp/watchdog.py`，系统 cron 每 10 分钟一次（`/etc/cron.d/dafeiyu-watchdog`）。纯 Python，**不调用 AI、不耗 token**，在服务器上跑，电脑关机也不影响

| 发现的问题 | 自动处理 | 刹车 |
|---|---|---|
| 推送跑完 5 分钟内日志里没有 `Message sent` | 调 AstrBot 后台「立即执行」接口重跑一次 | 每条最多补发 1 次；还失败就放弃，交给日报 |
| AstrBot 没在运行 | `systemctl restart astrbot` | — |
| MCP 工具箱没连上 | 重启 AstrBot | 1 小时最多 1 次 |
| 图库 < 6 张 | 后台补货 | 已在补货就不重复开 |
| 磁盘 > 90% | 删 3 天前的临时图 | 只删 `dafeiyu_*` |

- **踩坑**：AstrBot 的 API Key 不支持 `system` 权限（`Invalid scopes: system`），而「立即执行」接口要求它 → 改成用本机 `cmd_config.json` 里的 `jwt_secret` 现签一个 **5 分钟有效** 的后台令牌（后台登录用的就是这种令牌），不落盘、不打印
- **测试过程**：
  1. 令牌：只读调用 `GET /api/v1/cron/jobs` → 返回 11 个任务 ✅
  2. 首次运行：没有需要修的 → 无动作、无报错 ✅
  3. 真实演练：建一个「什么都不要发」的临时任务（12:33）→ 12:40 看门狗发现没发出并补发 ✅ → 12:50 补发仍没发出，按规则放弃 ✅（没有无限重试）→ 删掉演练任务，记录留在 `watchdog.drill.log`
  4. 加固后：`/usr/bin/time` 实测 0.44 秒、33 MB；`healthcheck.sh` 新增看门狗心跳检查 ✅；服务器日报出现「看门狗 · 0 分钟前巡检」✅
- **日报联动**：推送行补发成功显示「已补发」；数据栏「自动修复 24h N 次」；服务栏「看门狗」心跳灯
- **新规则**：R9（自动修复要有刹车）、R10（监控程序自己也要被监控，而且要轻）

### 2026-11-22 中午：服务器日报单独成卡 + 自我监控
- **需求**：服务器状态原来只是日报底部一条，看不出来 → 单独一张图，06:05 推送
- **新工具** `server_report`：资源圆环、服务状态灯、**过去 24 小时每条推送是否真的送达**、图库/备份/快照/网易云登录
- **送达检查怎么做的**：对每个任务，取它上次运行的时间，去服务器日志里看「运行后 5 分钟内」有没有 `send_message_to_user ... Message sent`：
  - 有 → √ 已送达；没有 → × 没发出（顶部会写「需要注意：xxx 没发出」）；24 小时内还没轮到 → · 还没到时间
- **验证**：临时任务 12:13 真实发送 ✅，图里正确标出了「叫床 07:20 没发出」「午饭 12:00 已送达」
- **已知局限**：
  - 用的是「时间窗口」判断：如果某个任务失败了，但 5 分钟内恰好有别的任务发了消息，会被误判成已送达（目前任务之间都隔开了 ≥5 分钟，基本不会发生）
  - 服务器日报**不能检查它自己今天这一次**，要到第二天的日报里才看得到
